### The change: the fill-window guard could not see its own failure mode (read 202)

Read 202's registered source is `main.log` warnings of `fill window too short`. There are **zero in the entire
54 MB log**, and the string does exist (`autoTrader.ts:3607`), so the read's own evidence says either the window is
wide enough or the detector is blind. It is both, and the second half is the defect.

`reconcilePending` classified a pending maker row that had left the resting list in this order:

    if (newlyFilled > 0.005) { promote }
    else if (filledTotal <= 0.005) { emit autoexpired }
    else if (filledTotal < p.promoted) { warn 'fill window too short' }

The failure the guard exists for (audit B-53) is that the newest-200-fills window no longer reaches an order's
earlier slice. When it reaches **part** of the order, `0 < filledTotal < promoted` and the warning fires. When it
misses the order **entirely** - the worse case - `filledTotal` is 0, so `filledTotal <= 0.005` catches it first and
the row is reported as an ordinary unfilled expiry: no warning, no episode row, the remaining slice never promoted.
The guard could only ever observe the milder half of its own defect.

Fix, in `src/main/strategies/autoTrader.ts`: one exported pure classifier, `pendingFillOutcome(filledTotal,
promoted)`, returning `promote` / `window-short` / `expired` / `none`, with `window-short` tested **before** the
expiry. Exactly one input changes verdict - `promoted > 0, filledTotal = 0` moves from `expired` to `window-short`
- and the case that previously fell through every branch (`filledTotal === promoted`, fully promoted) still emits
nothing, which is why the classifier needs a fourth value rather than a two-way swap.

**And the window itself measures adequate, so it was not widened.** Measured on the fresh dump: the newest 200
account fills span at least **26 h** over the last seven days (median 58 h), against a p99 filled-order lifetime of
**6.8 h** and a maximum of 23.8 h; 0 of 3,374 filled orders are currently part-filled with size remaining. The code
comment's premise - "356-687 fills a day" - is stale: this account now averages about **127 a day** (3,814 fills over
30 days), so the window covers more wall clock than it did when the audit was written, not less. Over the whole month
the tightest window is 5.75 h, which is the only regime where the tail could bite; the comment now records the
measurement instead of the old rate.
